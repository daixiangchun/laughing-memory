# 评测方法与结果

## 评测要回答的问题

1. **版本过滤有用吗？** 对比 `pre`（在版本子集内召回）、`post`（先全局召回再按版本过滤）、`none`（不过滤）三种方式的 Recall@K。
2. **冲突和拒答判得准吗？** 统计冲突误报、冲突漏报、误拒答。
3. **阈值定得合理吗？** 用相关问句与无关问句的相似度分布给出依据。

## 数据集

`backend/data/eval/questions.jsonl`，28 道题，每题标注期望状态（`answer` / `conflict` / `refused`），部分标注期望符号与版本：

按**期望状态**分：

| 类别 | 数量 | 说明 |
| --- | --- | --- |
| 应正常回答（answer） | 22 | 单版本提问，覆盖两个库的四个版本 |
| 应返回冲突（conflict） | 2 | 不指定版本提问跨版本不一致的符号（`p3`、`s2`） |
| 应拒答（refused） | 4 | 三题领域外（量子计算 / 红烧肉 / K8s）+ 一题不存在的符号 |

按**库**分：pandas 18 题、SQLAlchemy 7 题、不限定库 3 题（合计 28）。

其中标了期望符号的 24 题用于算 Recall@4；剩下 4 题（拒答类）只算状态准确率。已移除的符号（`append`、`lookup`、`iteritems`、`mad`）与新增的符号（`map`）各有专门题目。

数据集刻意**小而有针对性**：目标不是刷分，而是让每个决策点都有一道题可以现场演示。

## 指标定义

- **Recall@4**：期望符号出现在融合后前 4 条结果中即为命中。只统计标注了期望符号的 24 道题；期望状态为 `refused` 的题不计入。
- **状态准确率**：`status` 与期望一致的题占比。
- **冲突率 / 拒答率**：返回 `conflict` / `refused` 的题占比。
- **冲突误报**：期望为 `answer` 却返回 `conflict`；**冲突漏报**：期望为 `conflict` 却返回其他状态；**误拒答**：期望 `answer` 却返回 `refused`。

## 结果（28 题，Top-4，阈值 0.40）

| 版本过滤 | Recall@4 | 状态准确率 | 冲突率 | 拒答率 |
| --- | --- | --- | --- | --- |
| pre（先过滤） | **0.875** | **1.000** | 0.071 | 0.143 |
| post（先召回） | 0.875 | 1.000 | 0.071 | 0.143 |
| none（不过滤） | **1.000** | 1.000 | 0.071 | 0.143 |

错误计数：冲突误报 **0**，冲突漏报 **0**，误拒答 **0**。

复现：

```powershell
.\.venv\Scripts\python.exe backend\scripts\run_eval.py
# 结果写入 backend/data/eval/results.json，管理页 /admin.html 读取展示
```

## 怎么读这些数字

**为什么不过滤的 Recall 反而更高？** 因为不限制版本时，候选池是全部四个版本的文档，同一个符号在另一版本下的块也算命中。这正说明「不过滤」以准确率为代价换取覆盖率：它会把 1.5.3 的 `append` 当成 2.2.0 的答案，用户拿到的可能是过时信息。本项目默认 `pre`，原因就在这里。

**pre 和 post 结果相同？** 在 3195 个块、每版本数百块的规模下，`post` 的多取候选（`VECTOR_CANDIDATES=20`）足够覆盖过滤后的需求，所以两者打平。规模再大几个数量级时，`post` 的候选流失会显现，这也是保留两种模式做对比的原因。

**状态准确率 1.0 是否可疑？** 题目是按当前索引能力挑选的：语料明确覆盖了这些符号及其跨版本差异。它说明**规则与数据是对齐的**，而不是说系统能回答任意问题——语料之外的符号会走拒答，这一点由「DataFrame.nonexistent_method」和三个领域外问题验证。

## 阈值依据

实测最佳向量相似度：

| 类型 | 示例 | 分数 |
| --- | --- | --- |
| 相关（符号名出现在问题里） | `DataFrame.append 怎么用？` | 0.53 ~ 0.56 |
| 相关（类名 + 属性） | `sqlalchemy.orm.Session 怎么创建？` | 0.84 |
| 无关（领域外） | `今天天气怎么样` / `如何做红烧肉` | 0.25 ~ 0.26 |

取 **0.40** 作为下限，位于两类之间。另外：当问题中明确点名了知识库里存在的符号时，符号覆盖本身即视为足够证据，不再单独因相似度略低而拒答（例如 `engine.Engine 的 echo 参数` 相似度 0.381，但符号确实存在）。

## 已知偏差与改进

- 评测集由项目作者编写并标注，存在主观性；下一步应补充「从真实提问日志中采样」的题。
- 28 题样本量小，单个错误就会让指标跳动 3~4 个百分点；扩大规模前不宜过度解读小数点。
- 未评估生成质量（忠实度、引用正确性）。这需要人工或模型评审，当前只验证了检索与状态判定。
- 评测的**状态判定**（answer / conflict / refused）不依赖大模型：检索、冲突检测、拒答规则都是确定性的，所以换模型或模型不可用时这些指标不变。
- **答案文本质量目前没有度量**。`results.json` 的 `generation` 字段记录了「真实模型调用次数」与「退化为文档摘录次数」：前者为 0 时，答案文本是文档原文摘录，不能代表接入模型后的水平。下一步需要人工或模型评审来评估忠实度与引用正确性。
