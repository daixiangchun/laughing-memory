# 技术决策记录（ADR）

每条三行：背景 → 选择 → 代价。

## 切分：按 API 符号切，不用固定 token

- 背景：固定长度切分会截断代码示例和参数表，也让「同一符号跨版本对齐」无从下手。
- 选择：Sphinx 文档按 `<dl class="py ...">` 切成「一个符号一个块」，抽取签名、参数名、正文、代码、弃用标记。
- 代价：强依赖文档结构（Sphinx），换文档框架要重写解析器；一个符号的文档很长时块偏大。

## 版本元数据：chunk 级携带 library / version / symbol

- 背景：通用 RAG 只有文本，无法回答「这个说法属于哪个版本」。
- 选择：入库时写入三个字段，检索与冲突检测都以它们为准。
- 代价：语料必须按版本抓取和切分，抓取量随版本数线性增长。

## 版本过滤：默认 pre-filter，保留 post-filter 做对比

- 背景：全局召回后过滤会导致候选大量流失；先过滤则受限于子集大小。
- 选择：默认在版本子集内召回（pre），同时实现 post 与 none 用于评测对比。
- 代价：pre 的子集小、召回受限；评测显示在当前规模下 pre 与 post 打平、none 召回更高（见 evaluation.md）。

## 缺失符号：生成 missing 记录，而不是「查不到就算了」

- 背景：「某符号在 2.2 不存在」是判断版本冲突的关键证据，但页面上没有这句话。
- 选择：以该版本官方 `objects.inv` 符号清单为准生成占位记录；缺失记录**不进入检索索引**，只参与冲突判定。
- 代价：缺失记录必须与真实块分开存储（`missing.jsonl`），否则会在检索中压过真实文档，导致「检索到了却判证据不足」。

## 冲突检测：结构化字段为主，不做语义矛盾判断

- 背景：判断两段自然语言描述是否矛盾只能靠模型，成本高且不稳定。
- 选择：比较存在性、弃用标记、参数集合、签名四项可稳定抽取的事实。
- 代价：措辞不同但语义一致的情况可能误报，语义矛盾但字段一致的情况会漏判。

## 拒答：三条件触发，阈值来自实测

- 背景：宁可拒答也不编造，但阈值定高会误伤、定低会放行。
- 选择：相关性低于 0.40、符号未覆盖、冲突且未指定版本 → 拒答或返回冲突；用户点名了存在的符号时，符号覆盖替代相似度作为证据。
- 代价：覆盖率下降；阈值与实测分布绑定，换嵌入模型必须重新标定。

## 检索：向量 + BM25，RRF 融合

- 背景：纯向量对精确符号名不敏感（`DataFrame.append` 与 `DataFrame.items` 语义接近）；纯关键词对自然语言提问不敏感。
- 选择：两路各召回 20 条，用 RRF（只依赖排名）融合。
- 代价：多一次关键词打分与索引存储；BM25 为自实现，未做停用词与词干化。

## 精确符号优先：用户点名即最高相关性信号

- 背景：长点号符号在向量和 BM25 下都不稳定（`sqlalchemy.orm.Session` 会被 `object_session` 抢走）。
- 选择：解析问题中的形似符号 token，命中知识库后把该符号的块提到结果最前。
- 代价：误识别（普通英文缩写带点）可能引入噪声，用停用词表兜底。

## 向量库：FAISS，而非 pgvector

- 背景：原计划用 PostgreSQL + pgvector 让元数据与向量同库；但本机无法访问 Docker Hub，pgvector 镜像只能走镜像源。
- 选择：FAISS（全局索引 + 每版本子索引），元数据存 JSONL，缺失记录单独存放。
- 代价：没有 SQL 级过滤与事务，多进程写入会互相覆盖；规模到数百万块时需要迁移到服务化向量库。

## 嵌入：本地 MiniLM，而非 API

- 背景：建库要处理上千个块，走 API 有成本与延迟，且文档不应外传。
- 选择：`all-MiniLM-L6-v2`（384 维、归一化、内积即余弦）。
- 代价：首次要下载约 90MB 模型；中文效果弱于专用中文模型，换模型必须重建索引。

## 生成：OpenAI 兼容接口 + 不可用时退化为摘录

- 背景：不同环境（公司内网、本地 Ollama、云端 API）都需要能跑。
- 选择：只依赖 `base_url + key + model` 三个配置；未配置或调用失败时返回文档原文摘录，并在 `meta.used_llm=false` 标明。
- 代价：摘录模式的可读性不如模型组织后的答案；用户需自行分辨两种模式。

## 前端：原生 HTML/JS + Tailwind CDN + highlight.js

- 背景：面试演示优先，不需要构建链；重点是后端链路。
- 选择：问答页（会话列表 + 版本选择 + 冲突/拒答分支渲染）+ 管理页（索引状态 + 评测对比 + 逐题明细），由 FastAPI 同源托管。
- 代价：无组件化与状态管理，页面增多后维护成本上升；CDN 依赖外网，生产应本地打包。

## API 与前端：同源托管，不做 CORS

- 背景：前后端分开部署才需要跨域配置。
- 选择：静态文件挂在 `/`，接口在 `/api/v1/*`，前端走相对路径。
- 代价：静态挂载必须在所有 API 路由之后注册，否则会抢走 `/api` 请求。

## 查询日志：写 PostgreSQL，best-effort

- 背景：需要回答「用户问了什么、判成了什么、慢在哪、哪些问题被拒」，文件无法做按状态/时间的聚合。
- 选择：PostgreSQL `query_logs` 表，每次 `/api/v1/query` 写一条；写入失败只记 warning，不影响问答返回；管理页通过 `/api/v1/query/logs` 读取聚合结果。
- 代价：多一次数据库往返（本机 10~20ms）；单机直连未池化，高并发下需要换 `psycopg_pool`。

## 生成不可用时退化为文档摘录，而不是报错

- 背景：模型调用会因网络抖动、代理证书、密钥或模型名问题失败；如果直接抛异常，单次问答 500、批量评测中断。
- 选择：捕获后返回文档原文摘录，`meta.used_llm=false` 并在 `generation_note` 写明原因；检索、冲突检测、拒答判断都不依赖模型，照常工作。
- 代价：两种模式答案质量不同，前端需要显式标注「文档摘录模式」，避免用户误以为是模型组织过的回答。
